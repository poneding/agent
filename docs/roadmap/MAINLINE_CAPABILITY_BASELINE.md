# Mainline Capability Baseline

M55 resets the roadmap around the product goal: a local coding agent with one Rust runtime, CLI/TUI/Desktop surfaces, multiple model providers, explicit permissions, durable recovery, and auditable execution. This baseline is grounded in the current repository shape, crate tests, `xtask` commands, README command surface, and M01-M54 milestone history.

## Status Legend

| Status | Meaning |
|---|---|
| Strong | Core contracts and tests exist; remaining work is mostly product integration, UX, or scale. |
| Partial | Useful foundations exist, but the user-visible workflow is incomplete or uneven. |
| Early | Skeletons, contracts, fixtures, or narrow demos exist; substantial product work remains. |
| Missing | No meaningful implementation evidence was found. |
| Unknown | Verification needs a named command or file inspection before planning can trust it. |

## Executive Summary

The runtime platform is ahead of the product. `agent` has broad foundations for typed events, storage, tool execution, policy, context, memory, scheduler tasks, worktrees, teams, plugins, MCP, CLI/TUI/Desktop bridge contracts, observability, evals, and packaging. The product gap is the vertical daily-driver experience: a developer should be able to open a repo, ask for a small change, watch safe tool use, review edits, run tests, inspect trace/audit evidence, recover after interruption, and continue from CLI/TUI or Desktop.

The next mainline milestones should therefore prioritize vertical product flows:

- M56 proves one local coding-agent golden path.
- M57 makes provider choice a product capability.
- M58 improves project context selection.
- M59/M60 polish CLI/TUI and Desktop daily-driver surfaces over the shared runtime.
- M61-M65 productize task UX, recovery, worktree/team workflows, memory, packaging, and beta gates.
- M66 returns to extension/MCP hardening only after core product paths are credible.

## Cross-Cutting Risks

| Risk | Current Evidence | Mainline Response |
|---|---|---|
| Runtime breadth can hide missing product flow | Many crate-level tests prove components, but fewer tests prove one real coding workflow end to end. | M56 must ship one deterministic golden path with trace, audit, diff, tests, and final summary evidence. |
| CLI/TUI/Desktop parity can drift | Surface crates have separate tests, but product workflows are not yet proven across the shared runtime bridge. | M59/M60 must consume shared events/commands and reuse M56 smoke scenarios. |
| Provider support is narrower than product ambition | Fake and OpenAI-compatible paths exist; native provider capability negotiation is incomplete. | M57 must create provider capability diagnostics before adding more product UX. |
| MCP implementation depth can pull roadmap focus | M30-M54 added deep MCP foundations and MX01 drafts remain in the working tree. | Treat MCP as extension depth; mainline owners remain M56-M65 unless product workflow evidence says otherwise. |
| Recovery claims need user-visible proof | Checkpoint/replay contracts exist, but day-to-day resume/fork UX is not yet central. | M56 should include trace/replay evidence; M62 should productize recovery UX. |

## Immediate Implications

- M56 should start with repository session bootstrap and should not wait for more MCP work.
- M56 acceptance must include fake-provider deterministic evidence and at least one documented real-provider configuration path that does not break when unavailable.
- M57 should focus on provider capability matrix and diagnostics before broad UI polish.
- M58 should improve context selection for coding tasks before expanding memory personalization.
- M59/M60 should turn existing CLI/TUI/Desktop bridge foundations into daily-driver workflows.
- M65 release readiness should not be declared from `cargo xtask ci` alone; it needs product smoke artifacts for the golden path.
